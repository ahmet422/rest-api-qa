API contract (OpenAPI)

What “contract” means here, why teams care, and how Swagger UI helps you explore this lab’s API without guessing.

What is an API contract?

A normal contract is a written agreement: both sides know the rules. An API contract is the same idea for software: it describes what the server promises and what callers must send—paths (URLs), HTTP methods, request bodies, headers, status codes, and the shape of responses.

It is not the implementation inside the server; it is the published surface—like a restaurant menu listing dishes and prices, not the recipe in the kitchen.

In this project the machine-readable contract is expressed in the OpenAPI format (often still called “Swagger spec” in conversation). Your browser can load a human-friendly view of that spec—see below.

Why do we need it?

  • Less guessing. Testers and front-end developers know which endpoints exist and what fields are required—without reading Java source line by line.
  • Parallel work. Teams can agree on the contract first, then implement or automate against it.
  • Better tests. You can design cases around documented status codes (success, validation errors, auth) like those described in REST basics.
  • Living docs. When the app exposes OpenAPI (as SpringDoc does here), the description stays aligned with what the server actually serves—especially useful in class demos.

What is Swagger? Is it the same as OpenAPI?

OpenAPI is the standard name for the specification file (YAML or JSON) that describes the API.

Swagger started as the earlier ecosystem around that idea; today people often say “Swagger” to mean Swagger UI—the interactive web page where you can read endpoints, see schemas, and sometimes “Try it out” and send requests.

Short memory trick: OpenAPI = the document; Swagger UI = a friendly viewer for that document. This lab serves both the raw JSON and the UI—links in the next section.
