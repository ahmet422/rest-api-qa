CI/CD — for QA testers

This page is written for testers joining a dev team: what Continuous Integration and Continuous Delivery / Deployment mean, why they matter to quality, how environments line up, how GitHub Actions fits this lab, and what usually happens in industry.

What is CI/CD?

Continuous Integration (CI) — Developers merge work into a shared branch often. Each merge triggers an automated pipeline: build the app, run unit/API tests, sometimes lint or security scans. The team sees pass or fail quickly, on a machine that is not “someone’s laptop.”

Continuous Delivery / Deployment (CD) — After CI is green, changes move toward real users. Delivery usually means “release-ready artifact” (installer, container, deployable package). Deployment means actually pushing it to a server. CD can be manual approval or fully automated.

Examples (easy to remember)

  • Without CI: Five developers merge Friday afternoon. Monday morning QA finds login broken—nobody knows which change caused it.
  • With CI: The moment a change breaks compilation or an automated API test, the pipeline fails and the pull request is blocked until fixed.
  • CD in one sentence: “When CI is green and the business agrees, the same tested bits go to staging or production without re-building by hand on someone’s machine.”

Why is it needed — especially for QA?

  • Early signal (shift-left). You get cheap feedback before hours go into manual regression. Automated checks don’t replace exploration—they guard core paths and contracts.
  • Repeatable evidence. “It passed on CI” is a shared baseline: same JDK, same command (mvn verify), same clean checkout. That reduces “works on my machine” debates.
  • Gate before merge. Many teams require green checks on pull requests. QA benefits because risky code is less likely to land on main silently.
  • Frees time for deeper testing. Robots run smoke/API regression every push; you spend calories on edge cases, usability, and integration risks CI doesn’t cover.

Example: If this bookstore API loses JWT validation, an integration test in CI should fail before that build is promoted to QA or prod.

Environments: local, dev, QA, prod

Names vary by company (“test”, “staging”, “pre-prod”). The idea is progressive trust: cheap experiments first, real users last.

Environment Typical purpose QA angle
Local Developer or tester machine; fast feedback while coding or scripting tests. You run the app + Postman/REST Assured here (this lab uses H2 on dev profile).
Dev Shared unstable server; integrates latest branches; may break often. Smoke tests, API contract checks, pairing with devs; expect churn.
QA / Test Candidate build meant for structured test cycles; closer to production settings. Full regression, exploratory testing, bug bashes; sign-off often tied to release.
Prod Real customers, real data, real money and reputation. Monitoring, production verification after deploy, incident response—not where you try risky experiments.

Practice tip: Always know which URL and data set you are hitting. “Bug in QA” that was actually reproduced on an old dev server wastes everyone’s time.

How this works in IT — and QA-friendly best practices

  • Pipeline stages. Typical flow: build → unit tests → integration tests → publish artifact → deploy to dev/QA → manual/automated gates → prod. CI covers early stages; CD covers promotion.
  • Branch strategy. Short-lived feature branches, pull requests, reviews, required checks. Trunk (main) stays releasable when discipline holds.
  • Test pyramid. Many fast unit tests, fewer integration/API tests, even fewer end-to-end UI tests—each layer runs in CI where practical.
  • Flaky tests. Intermittent failures erode trust. Teams treat flakiness as debt: quarantine, fix, or replace—QA should flag unreliable automation loudly.
  • Configuration & secrets. Non-prod uses non-prod databases and keys. Test data must never default to copying real customer PII without controls.
  • Definition of Done. Often includes “CI green + reviewed + tested in QA environment.” Align with your team so expectations match reality.

In mature orgs, testers help choose what belongs in CI (smoke suite), what runs nightly (full regression), and what stays manual (exploratory charters).

GitHub Actions — in this lab’s context

GitHub Actions runs workflows when events happen on GitHub (push, pull request, schedule, etc.). Workflows live under .github/workflows/.

Besides the main build, this repo uses Dependabot (.github/dependabot.yml) for weekly dependency update PRs. Separate workflows cover dependency review on PRs, secret scanning, optional semantic PR titles, and nightly mutation testing—each is explained below.

This automation is CI (build + quality gates). Deploying to Azure/AWS/GCP would be extra CD steps (not configured here, and Docker is intentionally out of scope).

Pipeline steps — what runs and why

Locally, mvn verify runs the same Maven phases the CI job relies on. On GitHub, the main workflow also installs Node and runs Spectral after tests (needs target/openapi.json from integration tests).

  1. Spotless (Google Java Format). Enforces a single formatting style so reviews focus on behavior, not whitespace. Fail here means run mvn spotless:apply locally, then commit.
  2. Checkstyle. Static style rules (imports, naming, etc.) from config/checkstyle/. Complements Spotless: formatters fix layout; Checkstyle catches structural smells.
  3. JaCoCo prepare-agent. Attaches the coverage agent before unit tests so execution data is recorded.
  4. Compile + test-compile. Ensures main and test sources build on a supported JDK (CI uses Temurin 17 and 21 in a matrix).
  5. PMD. Rule-based bug and smell detection on source code (config/pmd/ruleset.xml). Runs after tests are compiled so analysis stays cheap but accurate enough for teaching defaults.
  6. SpotBugs + FindSecBugs. Bytecode analysis for likely bugs and a subset of security-oriented patterns. Some findings are suppressed in config/spotbugs/exclude.xml where the tool cannot see application-level guarantees (documented there).
  7. Surefire — unit tests (*Test.java). Fast tests including WireMockBasicsTest, which shows how to stub HTTP dependencies without hitting real servers.
  8. Package + CycloneDX SBOM. Produces the runnable jar and a Software Bill of Materials (target/bom.json) listing components and versions—useful for supply-chain visibility and audits.
  9. JaCoCo prepare-agent-integration + Failsafe (*IT.java). Integration tests start Spring Boot (profile test, H2). Coverage from this fork is appended to the same execution file so reports include API-level exercise. OpenApiExportIT downloads /v3/api-docs into target/openapi.json for the next step.
  10. JaCoCo report + check. HTML/XML coverage under target/site/jacoco/ and a minimum line coverage ratio on the whole bundle so coverage cannot silently regress to zero.
  11. Spectral (CI only). Lints the exported OpenAPI JSON against .spectral.yaml—catches contract issues (schemas, required fields, operations) before humans rely on wrong docs.
  12. Artifact uploads (CI). Stores bom.json and JaCoCo HTML per JDK version for download from the Actions run—handy for assignments and debugging coverage locally vs CI.
  13. Dependency review workflow. On pull requests, GitHub compares declared dependencies against known vulnerabilities (requires dependency graph; available on public repos).
  14. Secret scan (TruffleHog). Scans changed commits for leaked credentials. Verified findings should block merges; tune noise via workflow options if a lesson adds intentional test tokens.
  15. Semantic PR title check. Encourages conventional prefixes (feat:, fix:, chore:, …) so change logs and release notes stay readable. Remove or relax this workflow if your course does not require it.
  16. Nightly PIT (mutation testing). Profile pitest exercises tests against small mutations in com.mindtek.bookstore.service.*. Slower than normal CI; scheduled so it does not slow every push. Reports upload as workflow artifacts.

Classroom demo: branch → PR → green CI → merge

  1. Create a branch (e.g. lesson/ci-demo).
  2. Make a tiny change (README line or pom.xml version bump).
  3. Push and open a Pull Request into main or master.
  4. Watch Checks until the workflow passes.
  5. Merge after review — optional: enable branch protection to require green CI.
