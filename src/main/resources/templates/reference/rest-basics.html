REST basics

You don’t need to be a backend developer to understand APIs. This page is written like a short lesson—take it in order, pause on the metaphors, and come back to the Quick reference at the bottom before you practice.

Tip: when we say “client,” we mean whoever starts the request—the browser, Postman, or a test script—not “your customer.”

Start here: how do apps even talk?

Have you ever wondered how the screen you click and the server far away stay in sync—or how two separate systems (a mobile app and a bank, a shop website and a payment service) exchange information?

They don’t read each other’s minds. They send structured messages over the network, usually using HTTP—the same family of rules your browser uses to load a normal web page. A REST API is one popular style of designing those messages so everyone agrees: “this address means books,” “GET means read,” “here’s how success or failure looks.”

Metaphor you can reuse in class

Treat one HTTP request like sending a registered letter. You need an address (URL), a clear instruction on what to do (method), sticky notes for special handling (headers), and sometimes a parcel inside (body). The server sends a reply letter back: a status (“delivered / refused / wrong address”) and maybe more pages inside (response body).

Client and server — who asks, who answers?

In almost every web system you teach or test, work splits into two sides. The client is what sits close to the user: the browser tab, a mobile app, Postman, or an automated test runner. It starts the conversation (“please send me the book list”). The server is a program running somewhere else—often in a data centre or your laptop for demos—that waits for those asks, runs rules (validation, permissions), talks to a database if needed, and sends an answer back.

Between them is the network (LAN, Wi‑Fi, internet). Messages follow agreed rules—here, HTTP—so both sides understand the same verbs and status codes. One server can serve many clients at once; each client only cares about its own request–response pair.

In this lab: your browser or Postman plays client; the Spring Boot app is the server; the database sits behind the server (clients never connect to it directly).

What is a REST API, in one breath?

Imagine the server runs a library. It publishes addresses (URLs) for things (resources)—for example “all books” or “book number 42.” Your client picks a standard action (HTTP method): look at the shelf, borrow something new, replace a whole record, or remove it. The server answers with a response: almost always a status code (three digits) and often a body—today usually written as JSON text.

In this lab the star resource is books. Exact paths live under This API.

Resources and paths (nouns, not verbs)

Good REST style puts nouns in the URL, not commands like “getAllBooks.” The path names what; the method names what you’re doing.

  • A collection — /api/books — think “the whole shelf.”
  • A single item — /api/books/42 — “the book whose id is 42.”

The four methods you’ll use most

They map to everyday testing work; they aren’t the entire HTTP encyclopedia.

Method Remember it as…
GET Look, don’t touch. Read data; repeating it shouldn’t break anything.
POST Create something new. Here: add a book—or log in and “create” a token.
PUT Swap the whole thing. Same id, full replacement body.
DELETE Remove. Second delete in this app? See Idempotency.

Headers — the sticky notes on your envelope

Headers are small name: value lines that travel with the request or response. They don’t replace the body; they tell both sides how to interpret what follows.

  • Content-Type — “The body speaks this language.” For JSON payloads you’ll see application/json. If you forget it, the server may not parse your body.
  • Authorization — “Here’s how you know who I am.” With JWT you’ll send Authorization: Bearer <token>.
  • Accept — “I’d prefer the reply in this format,” e.g. JSON. Servers can sometimes offer more than one format.
  • Content-Length (often automatic) — how many bytes the body has. Handy when debugging “empty body” mysteries.

Memory trick: if the body is the letter inside the envelope, headers are the printed instructions on the outside—still part of the same shipment.

JSON and XML — two ways to pack the same idea

Both are just text formats for structured data. Many older enterprise systems love XML; most modern REST tutorials (including this lab) default to JSON because it tends to be shorter and quicker to read.

JSON XML
Shape Curly braces { }, arrays [ ], “key”: value pairs. Nested tags, like HTML: elements open and close.
Tiny example {"title":"Clean Code"} <book><title>Clean Code</title></book>
Verbosity Usually compact—fewer characters on the wire. Often more verbose; repeats tag names.
In this lab Yes — requests and responses use JSON. Not required here; you may still meet XML in legacy APIs elsewhere.

Whether JSON or XML, the server still checks Content-Type so it opens the “parcel” with the right parser—like choosing subtitles vs. dubbing on the same movie.

Status codes — the summary line on the reply

Every response begins with a three-digit code. Learn the families first; memorize favorites second.

  • 2xx — success. Examples: 200 OK, 201 Created, 204 No Content (success with nothing to show in the body).
  • 4xx — problem on the client side or permission. Examples: 400 bad input, 401 not authenticated, 403 authenticated but not allowed, 404 not found, 409 conflict (e.g. duplicate ISBN). Duplicate POST details: Idempotency.
  • 5xx — server trouble. Log it and escalate; it’s usually not your test data’s fault.

401 = “I don’t know you yet.” 403 = “I know you, but you can’t do that.”

Logging in — your badge goes in a header

This API uses JWT. Call POST /api/login (see This API), read the token from the response, then on later calls set Authorization: Bearer <token>. Same metaphor: the token is your visitor badge; the header is the clip that attaches it where reception expects it.

Quick reference

  • Client / server — client sends the request first; server hosts logic + data and returns the response.
  • Letter metaphor — URL + method + headers + optional body out; status + headers + optional body back.
  • Resource — thing the API exposes (books). Paths use nouns.
  • Methods — GET read, POST create, PUT replace, DELETE remove.
  • Headers — Content-Type, Authorization, Accept, …
  • JSON vs XML — both encode structure; JSON is usual for REST here.
  • Token — Authorization: Bearer <token> after login.
